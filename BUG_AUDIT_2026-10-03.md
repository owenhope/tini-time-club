# Bug audit — 2026-10-03

Five parallel read-only reviews were run, one per area: auth/startup, reviews/social, discovery/places/Passport, database, and admin/web plus edge functions. Each finding has a file:line reference and a failure scenario.

**Verification status**

- **Tested:** items marked **Verified (dev DB)** were reproduced on the `development` Supabase branch inside a rolled-back transaction, running as the `authenticated` role.
- **Code-read:** items marked **Confirmed (code)** were re-read by hand after the review flagged them. Everything else is the reviewer's finding, with its stated confidence.

The known random sign-out bug (LargeSecureStore) is **fixed**, as of commit 070d703 (`utils/sessionStorage.ts`): AFTER_FIRST_UNLOCK, retried reads, no purge on read error, a stable key and atomic writes.

The pending Regulars migration (`20261003120000_regulars_require_two_reviews`, PR #36) was reviewed and has **no defects**.

## P0 — security

### 1. ✅ FIXED 2026-10-04 (PR #38, migration 20261004120000, dev + prod) — Members can make themselves verified and fake their counts — **Verified (dev DB)**

- **Where:** `protect_profile_verification` (`supabase/migrations/20260728224000_verified_admin_badge.sql:13`), `protect_profile_review_count` (`20260731150000_complete_avatar_rank_counts.sql:12`), `protect_profile_follower_count` (`20260823122000_cursor_discovery_pages.sql:16`).
- **Why it fails:** these guard functions are `SECURITY DEFINER`, so `current_user` is always `postgres` inside them. The `current_user <> 'postgres'` check is therefore never true, and the exception never fires. `passport_points` (`20260904170000_martini_passport.sql:3`) has no guard at all.
- **Reproduced as a member:** `UPDATE profiles SET is_verified=true / review_count=9999 / passport_points=1000000 WHERE id=auth.uid()` all succeeded.
- **Fix:**
  - Make the guards `SECURITY INVOKER`.
  - Better: `REVOKE UPDATE ON profiles FROM authenticated`, then `GRANT UPDATE (<editable columns>)`.
  - Add a pgTAP `throws_ok` test that runs as `authenticated`.

## P1 — security / integrity

### 2. ✅ FIXED 2026-10-04 (PR #39, migration 20261004130000, dev + prod) — Members can insert locations directly (place_id hijack) — **Verified (dev DB)**

- **Where:** the "Individuals can create locations." policy (`20260727235610_remote_schema.sql:814`) plus the baseline `GRANT ALL`.
- **Impact:** a member can insert a row that claims a real bar's Google `place_id`. `publish_review_v1` and `resolve_or_create_location` then attach every later review of that bar to the fake row.
- **Fix:** drop the policy and revoke INSERT from anon and authenticated. The app already creates locations through the definer RPCs.

### 3. ✅ FIXED 2026-10-04 (PR #40, migration 20261004140000, dev + prod) — Direct comment inserts bypass `create_comment_v2` checks — **Verified (dev DB)**

- **Where:** the comments INSERT policy (`20260728000100_tighten_rls.sql:12`). It only checks `user_id = auth.uid()`.
- **Impact:**
  - A blocked member can comment on the blocker's review, and other members see it.
  - Members can comment on unpublished reviews.
  - Comment length is unlimited (a 5,000-character comment was accepted in the test).
  - Comment stamps can be farmed.
- **Fix:** have the policy's `WITH CHECK` require that the review is published and `is_member_visible(author)`, and add `CHECK (char_length(body) <= 500)`. Keep INSERT itself, because shipped builds insert comments directly.

### 4. ✅ FIXED 2026-10-04 (PR #41, deployed to tinitimeclub.com) — Public website shows private members' reviews — **Confirmed (code)**

- **Where:** `admin/lib/publicReview.ts:76,96`, `admin/lib/publicLocation.ts:73,89-92`.
- **Why it fails:** `/r/[review]` and `/p/[place]` use the service role and filter only on `deleted`, never on `profiles.is_public`.
- **Impact:** members who switched off "Visible to visitors" still appear to signed-out visitors and crawlers. Their username, avatar, review text, photos and comments all show. The `public-content` edge function filters `is_public` correctly; these website pages don't.
- **Fix:** select `is_public`. Return `notFound()` on `/r` when it is false, and drop those reviews and comments on `/p`.

### 5. ✅ FIXED 2026-10-04 (PR #42, migration 20261004150000, dev + prod) — `get_member_passport_v1` ignores blocks

- **Where:** `20260907230000_member_passport_backfill_on_view.sql:173`.
- **Impact:** a blocked member can read the blocker's stamps and points. The call also triggers a Passport reconcile on the blocker.
- **Fix:** add `AND is_member_visible(p_profile_id)`.

## P1 — broken behavior (app)

### 6. ✅ FIXED 2026-10-04 (PR #43, merged; ships with next OTA) — Whole app unmounts whenever the profile reloads — **Confirmed (code)**

- **Where:** `app/_layout.tsx:221-237,614`, `app/(tabs)/(home,discover,profile)/_layout.tsx:89`, `context/profile-context.tsx:257`.
- **Why it fails:** `isReady` is derived from `!profileLoading` and never latched after startup. `refreshProfile()` sets `loading=true`, so `RootLayoutNav` returns `null`.
- **Triggers:** Edit Profile save, avatar upload, favorite location, review submit, sign-in.
- **Impact:** the screen goes blank, the navigation stacks reset, and `router.back()` lands on the wrong screen.
- **Fix:** latch startup once it has resolved, and gate on `loading` only before the first resolution, in both layouts.

### 7. ❌ NOT A BUG (checked 2026-10-04) — Activity screen refreshes itself in a loop

**Already prevented** by trigger `activity_receipts_skip_noop_update` (`20260813123000_activity_receipt_noop_guard.sql`), which drops no-op receipt updates, so no realtime event fires. Verified on dev: a repeat mark-seen/mark-read leaves the receipt row untouched; the trigger is enabled in prod. The original review missed this migration.

~~Original report:~~

- **Where:** `mark_activity_seen_through` (`20260813120000_activity_center.sql:334`) does `ON CONFLICT DO UPDATE` with no `WHERE`, so it rewrites every receipt row on each call. `activity_receipts` is in the realtime publication, and `hooks/useActivityFeed.ts:233` refreshes on any change and then marks seen again. `context/activity-context.tsx:88` also re-runs the unseen count and the Passport reconcile each pass.
- **Impact:** an endless refresh, network traffic and battery drain while Activity is open.
- **Fix:** use `DO UPDATE ... WHERE activity_receipts.seen_at IS NULL`, and the same in `mark_activity_read` at `:393`.

### 8. ✅ FIXED 2026-10-04 (PR #44, merged; ships with next OTA) — Visitors see 0 followers / 0 following on every profile — **Confirmed (code)**

- **Where:** `components/UserProfile.tsx:254-256` sets the public counts. The reset effect in `hooks/useProfileScreenData.ts:175-189` then zeroes them, and the counts are only reloaded for signed-in viewers.
- **Fix:** apply the visitor counts after the reset, keyed on the profile id.

### 9. ✅ FIXED 2026-10-04 (PR #45, merged; ships with next OTA) — "Try again" after a keychain-locked launch drops a member into visitor mode

## P2 — edge cases (one line each)

### Auth

- **Token-less auth callback links:** splash stays up forever on cold launch, or stays stuck on "Signing you in" when warm (`utils/authDeepLink.ts:50,71`, `app/_layout.tsx:452,494`).
- **Push after sign-out:** an in-flight push registration can re-attach the token after sign-out (`services/pushNotificationService.ts:110-183`).
- **Google sign-in cancel:** cancelling shows an error alert (`components/GoogleAuth.native.tsx:29-43`; v13 returns `type:'cancelled'`).
- **Apple sign-in errors:** errors are silent, with no alert or loading state (`components/AppleAuth.native.tsx:77-82`).
- **Stale badge count:** a stale response can set the previous member's Activity badge count after sign-out (`context/activity-context.tsx:41-66`).
- **Old return path:** the pending membership return path never expires (`services/visitor-session.ts:23-32`).

### Social

- **Activity history gap:** a refresh during load-more leaves a permanent gap in Activity history (`hooks/useActivityFeed.ts:147-193`). This is worsened by #7.
- **Blocked reviews linger:** a blocked user's reviews stay in the home feed for up to 2 minutes (`components/UserProfile.tsx:324-343`).
- **Blocks not enforced on follow/like:** blocked members can still follow and like (followers, likes and comment_likes INSERT policies), and the followers read policy ignores blocks.
- **Share stamp farming:** share stamps can be farmed by repeated `log_review_share` calls (`20260801170000_review_share_events.sql:27`).

### Places and Passport

- **Profile review paging:** paging and refresh share a request counter and can get stuck (`hooks/useProfileScreenData.ts:94-165`).
- **Favorite location:** the profile's favorite location chip disappears after the viewer's own profile loads (`hooks/useProfileScreenData.ts:186,271-297`).
- **Map search:** older search results can overwrite newer ones (`components/map/search.tsx:50-89`).
- **"Show on map":** shows no pin or sheet for an unreviewed venue inside the already-fetched bounds (`components/explore/ExploreMap.tsx:579-649`).
- **Location page errors:** skeletons stay forever on error, and a transient refetch error wipes already-loaded data (`components/Location.tsx:71-76,243-247,333`).
- **Friday reminders:** they keep firing in the old timezone after the phone's timezone changes, and the comment says 5pm while the code uses 16:00 (`utils/martiniReminder.ts`).

### Database

- **Location merges:** `merge_locations_v1` sends a burst of bogus Regular joined/left notifications and doesn't refresh Golden Glass for the canonical location (`20260828100000:1003-1011`).
- **Push token takeover:** `register_push_token` hands an existing token to whoever calls it (`20260730120000:74`).
- **`handle_new_user`:** missing `SET search_path` (low risk).

### Admin / web / edge functions

- **Tracking leaks unsubscribe tokens:** Google Analytics runs on `/admin/*`, and both the Meta Pixel and Google Analytics run on `/email/unsubscribe?token=…`, so the unsubscribe token is sent to Meta and Google (`admin/app/layout.tsx:105-116`, `admin/lib/adTracking.ts:33`). The Pixel also auto-tracks client-side navigations, so PageViews may be double-counted unless `fbq.disablePushState = true`.
- **Public forms:** the claim and inquiry forms have only a honeypot, with no rate limit (`admin/lib/publicClaimAction.ts`).
- **Admin login:** comparisons are not constant-time, parallel brute force is unlimited, and changing `ADMIN_PASSWORD` doesn't revoke sessions (`admin/lib/actions.ts:32-40`, `admin/lib/session.ts:49`).
- **Account deletion order:** `delete-account` deletes storage before the database step, so a failure partway through leaves reviews pointing at deleted images (`supabase/functions/delete-account/index.ts:203-211`).
- **Broadcast retry:** retrying a failed broadcast notifies members a second time, because the `broadcastId` is new on each submit (`admin/lib/actions.ts:89-120`).
- **Email campaigns:** one hard-bounced address stops the whole campaign batch (`admin/lib/emailService.ts:141-153`).
- **Rate limits:** edge-function rate limits are keyed on a client-controlled `X-Forwarded-For`, held in memory per instance, and the counters grow without bound (`public-content`, `app-events`, `app-usage`).
